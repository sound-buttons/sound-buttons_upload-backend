## Why

The SoundButtons upload backend currently targets .NET 8 (LTS), whose support window ends well before that of the now-GA .NET 10 LTS. Upgrading to .NET 10 keeps the service on a longer-supported, patched runtime, unlocks newer language/runtime features and performance improvements, and realigns the container image with the maintained `dotnet-isolated10.0` Azure Functions base image so security and base-image updates continue to flow.

## What Changes

- Retarget the `SoundButtons` Azure Functions isolated-worker project from `net8.0` to `net10.0`.
- Upgrade the Azure Functions Worker SDK and Worker packages to the versions required to target .NET 10 on the Functions v4 host (this may cross the Worker `1.x` → `2.x` boundary). **BREAKING** for the build toolchain: the project will no longer build on the .NET 8 SDK.
- Upgrade framework-tied dependencies (e.g., `Microsoft.Extensions.*`, ASP.NET Core `FrameworkReference`) and review all remaining NuGet packages for .NET 10-compatible versions, including the Durable Functions, Storage Blobs, Application Insights, OpenAPI, and Serilog extensions.
- Update the multi-stage `Dockerfile`: switch the build image to the .NET 10 SDK and the runtime base image to a published .NET 10 isolated Functions tag — `4-dotnet-isolated10.0` (note: **no `-slim` variant is published for the .NET 10 isolated line**, so the current `...8.0-slim` cannot be mapped to `...10.0-slim`). The FFmpeg static-binary image tag `:8.0` is an FFmpeg version, not a .NET version, and is intentionally left unchanged.
- Update the cosmetic .NET version string in the outbound HTTP `User-Agent` (`Program.cs`).
- Review and update the Helm chart and `docker-compose.yml` for any .NET-version-coupled references and confirm the runtime remains `dotnet-isolated`.
- Update documentation (README and any developer-setup notes) to reference the .NET 10 SDK as the local prerequisite.
- Verify the GitHub Actions `docker_publish.yml` pipeline builds and publishes the image successfully on the new runtime (the build runs inside Docker, so no host SDK pin is expected to change).

This is a runtime/platform modernization. No HTTP API contract, function trigger, request/response schema, or externally observable behavior changes.

## Impact

- **Code**: `SoundButtons/SoundButtons.csproj` (target framework + package versions), `SoundButtons/Program.cs` (User-Agent version string). The auto-generated `obj/.../WorkerExtensions` project is regenerated by the upgraded Worker SDK.
- **Container / build**: `Dockerfile` (SDK build image + isolated runtime base image), `docker-compose.yml` (verification only).
- **Deployment**: `helm/` chart values/templates (verification of the `dotnet-isolated` runtime and image references).
- **CI/CD**: `.github/workflows/docker_publish.yml` (verified, expected unchanged aside from a green build on the new base images).
- **Docs**: `README.md` and developer setup notes.
- **Dependencies**: Azure Functions Worker SDK and all Worker extension packages; framework-coupled `Microsoft.Extensions.*` and ASP.NET Core references; and the third-party OpenAPI extension. The in-process `Microsoft.Azure.WebJobs.Extensions.OpenApi` package registered no endpoints on the isolated worker (a pre-existing architectural mismatch), so it is replaced with the isolated-worker `Microsoft.Azure.Functions.Worker.Extensions.OpenApi` package, confirmed working on .NET 10 / the upgraded Worker line.
- **Risk**: Possible incompatibility of the third-party OpenAPI extension and Worker `1.x`→`2.x` API surface changes; mitigated by validating a local container build and a successful CI image publish before merge.
